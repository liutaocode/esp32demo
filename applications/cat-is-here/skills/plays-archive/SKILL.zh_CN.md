# 归档已发布应用

按开发者要求选择目标。将源码推送到作者仓库，与向上游贡献纯文本摘要是两种
工作流。明确要求提交并推送作者仓库的 main，即授权该目标；不要替换成上游 PR 流程。

## 确定范围

1. 查询官方发布接口，以项目 ID、标题和源码仓库匹配本地实现。目录、旧送审 JSON、
   Git 提交或封面均不能证明已发布。区分项目发布状态与最新修订状态：已发布项目
   仍可能有新的草稿。源码修订无法准确对应时记录不确定性，不声称复现了发布固件。
   只有用户要求时才纳入待审核项目。
2. 建立明确的应用白名单，同时盘点独立仓库、Git worktree 和主工作区，排除无关实验。
3. 检查 Git 状态和远端引用。混合或未清理的工作区应使用独立 worktree 整理，保留用户
   改动。移动 worktree 应通过 Git 感知的方式处理；目录改名不会修复构建缓存。

## 作者源码仓库

- 将应用逻辑、必需字体和音频、素材许可、测试与构建配置整理完整。维护双语索引，
  列明社区 ID、源码位置、准确构建选择器或独立构建命令。
- 根据构建定义收集依赖，再在隔离副本中验证。原工程能编译可能掩盖缺失的字体或
  素材数据。即使固件只链接生成的 C 数据，也要收齐生成器和测试清单引用的输入
  （例如 PCM/MP3 原始素材）。构建脚本应创建忽略的输出目录，不能依赖私有审核
  文件夹已存在。可复用 BSP 与应用代码分开；不要为了归档精简而改变运行行为。
- 未知选择器必须报错，标签或目录名称不会自动选择固件。逐项构建纳入的目标并运行
  主机测试，明确报告不支持或失败的目标。保持
  `docs/development/engineering/ble-recovery-compatibility.md` 中的 BLE/Recovery 契约。
- 暂存前检查文本、二进制素材和推送会暴露的历史。检查字体生成注释、生成器默认值
  中的本机路径，以及作者和提交者邮箱。新提交使用已核实的 GitHub noreply 身份，
  保留上游署名。
- 排除令牌、凭据存储、设备二维码秘密、截图回执、串口标识、未清理日志和本地发布
  请求。固件成品与审核媒体不是源码依赖。但 `.bin` 也可能是必需的 ADPCM 音频，
  应按构建用途分类，不能仅看扩展名。
- 检查实际暂存的文件内容，而非只看工作区。模式扫描通过只代表所检查模式未命中，
  不代表绝对安全。不要把疑似秘密的值输出到报告。
- 集成前检查祖先关系：合并干净分支仍可能从另一父提交重新引入隐私元数据。
  如果清理已推送历史需要非快进更新，先准备并验证干净候选版本，再取得针对历史
  重写的明确授权。默认不强推。
- 主机检查使用 ESP-IDF 所用的受支持 Python 环境。在较新的系统 Python 中通过，
  仍可能在激活后的工具链环境中因类型注解失败。
- 运行 `./tools/validate.sh`，只提交审查后的文件，推送指定引用并回读远端提交 ID。
  不要把本地提交当作上传完成。没有要求时不创建上游 PR。

## 上游纯文本归档

仅在开发者要求向上游归档时使用。基于上游 main 创建独立分支或 worktree，在
`plays/<username>/<app-name>/` 写双语摘要，包括社区标题和描述、核实的交互、
送审时填写的源码地址及封面文件名/格式。合并 README 中相关事实。不要纳入源码、
固件、封面文件或私密发布记录。上游 PR 不修改作者自有的根 README。仅在获得
相应授权时推送到 fork 并创建上游 PR。

## 经验沉淀与交付

用户要求蒸馏错误时，以观察到的失败或明确纠正为依据，写清失败、后果和具体预防
检查。不要复制对话记录、私有路径、凭据或个人标识，不把某个应用的偏好泛化为
所有产品的规则。

报告源码范围、排除项、目标分支和已核实的远端提交。分别报告 `Build`、`Host tests`、
`Device tests` 和 `Unverified`。编译或历史截图不能替代新源码快照的实机验证。
